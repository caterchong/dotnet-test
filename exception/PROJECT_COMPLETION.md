## 🔬 核心发现

### 主要性能指标

```
┌─────────────────────────────────────────────────────────────┐
│                      性能对比总结                            │
├────────────────┬──────────────┬──────────────┬──────────────┤
│ 场景           │ 异常方式     │ 返回值方式   │ 性能差异     │
├────────────────┼──────────────┼──────────────┼──────────────┤
│ 正常情况       │ 2.917 ns ✅  │ 16.514 ns    │ 快 5.7 倍    │
│ 错误情况       │ 14,314 ns ❌ │ 7.846 ns ✅  │ 慢 1,823 倍  │
└────────────────┴──────────────┴──────────────┴──────────────┘
```

### 关键结论

1. **异常用于正常流时很快** → JIT 优化
2. **异常用于错误流时很慢** → 堆栈跟踪捕获昂贵
3. **返回值方式更一致** → 无论正常还是错误都快
4. **不要用异常做控制流** → 这是反模式

### 实战建议

```
错误频率判断:
├─ < 0.1%  → 可以考虑异常
├─ 0.1%-10% → 使用返回值
└─ > 10%   → 一定要用返回值，不用异常！
```

## 💡 应用建议

### 对于现有项目的改进建议

1. **代码审查**
   - 查找使用异常做控制流的代码
   - 检查异常发生频率高的地方
   - 考虑使用 Result<T> 或 TryXxx 模式替代

2. **性能优化**
   ```csharp
   // ❌ 之前
   try { return int.Parse(input); }
   catch (FormatException) { return 0; }
   
   // ✅ 之后
   if (int.TryParse(input, out var result))
       return result;
   return 0;
   ```

3. **API 设计**
   - 提供 TryXxx 方法供高性能场景使用
   - 为罕见的异常情况抛出异常
   - 清晰地文档化预期的失败情况

### 对于新项目的建议

1. **从一开始就设计好**
   - 评估错误的预期发生频率
   - 选择合适的错误处理模式
   - 避免性能陷阱

2. **使用适当的工具**
   - C# 的 TryXxx 模式 (.NET BCL 中广泛使用)
   - Result<T,E> 对于需要错误信息的场景
   - 异常仅限于真正的异常情况

3. **监控和测试**
   - 使用 BenchmarkDotNet 进行性能测试
   - 监控异常率
   - 定期审查性能指标
